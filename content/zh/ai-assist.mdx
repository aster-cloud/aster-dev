# AI 辅助与自带 Key

Aster Cloud 的策略编辑器可以借助大语言模型起草、补全和改进规则。你可以使用平台的 AI 额度，也可以为 OpenAI 或
Anthropic **自带 Key**（BYOK），并可选地绑定具体模型（ADR 0048）——调用费用记在你自己的 provider 账户上，组织对模型的规定也随之生效。

AI 的输出只是建议。在你亲自保存、批准、部署之前，它写的任何东西都不会生效；最终运行的规则，与你亲手写出来的
Aster 规则一样确定。

## AI 能做什么

- **行内补全**——输入停顿约半秒后，编辑器把光标所在行及其之前最多十行发出，并给出可以接受的补全。每次停顿即一次
  AI 请求。可在设置页或编辑器状态栏关闭，选择按浏览器保存。
- **AI 面板**——用自然语言描述规则即可得到草稿，也可以针对现有代码请求改进建议。草稿以与当前源码的差异形式展示，
  确认后才应用。
- **站内助手**——基于文档与命令面板回答问题。登录用户还会得到以检索结果为依据生成的答复；未登录时只做检索。

以上请求都经过 Aster Cloud 服务端：校验会话与额度，再签名调用策略 API 的 `/api/v1/ai/*` 端点。浏览器从不直接访问模型
provider。提示词到达模型之前，会先经过安全守卫：识别提示词注入，过滤与策略编写无关的话题，命中即拒绝。

## 平台额度还是自带 Key

没有自带 Key 时，AI 请求使用平台凭证，计入你所在套餐的每月 AI 额度。有可用的自带 Key 时，请求用你的 Key 发往你的
provider，不消耗平台额度，token 费用由 provider 向你计费。

## 添加 Key

打开 **设置 → AI 密钥**，填写：

| 字段 | 说明 |
| --- | --- |
| Provider | OpenAI 或 Anthropic。（Google Vertex AI 可以保存，但不用于 AI 辅助。） |
| 模型（可选） | 你的 Key 允许使用的模型 id。留空即使用平台默认。 |
| API Key | 加密保存；保存后只显示后四位。 |
| Provider URL（可选） | `https` 端点，例如 OpenAI 兼容网关。只有在管理员允许列表中时调用才能成功。 |
| Token 额度（可选） | 每月 token 数，正整数；达到后跳过该 Key。 |
| 失效日期（可选） | 未来的日期；过期后跳过该 Key。 |

保存时只检查自定义 Provider URL 是否为 `https`。策略 API 在**每次**调用它时——包括保存时的模型列表校验——都会对照管理员的
允许列表，并拒绝内网与内部地址。因此不在允许列表中的 URL 保存时不会被拒绝，只是模型校验无法进行（出现下文的「无法校验」提示），
而经这把 Key 的每次调用都会失败。

### 选择模型

模型 id 只能包含字母、数字与 `. _ : / -`，最长 128 个字符。保存时，Aster Cloud 经策略 API 向 provider 查询这把 Key
可用的模型：

- provider 返回了列表、而你填的模型不在其中——不保存，提示信息列出可用模型。
- 查询失败（provider 响应慢或短暂不可用）——照常保存，并提示「已保存，但暂时无法校验模型列表；将按所填模型调用。」
- 网关根本不提供模型列表——直接保存，不做存在性校验。

列表随 Key 保存（至多 200 个 id）并定期刷新。它只是提示，从不决定一次调用用哪把 Key 或哪个模型。模型留空时，
**模型**列显示「平台默认」；模型列表校验过之后还会给出模型名，例如 Anthropic 显示「平台默认（claude-sonnet-5-5）」。

## 一次调用用哪把 Key、哪个模型

你所有的 Key——不分 provider——组成**一个优先级队列**，先按优先级、再按添加时间排序。每次 AI 请求，Aster Cloud
沿队列取第一把满足以下条件的 Key：

1. 处于启用状态，且 provider 受支持（OpenAI 或 Anthropic）；
2. 未过失效日期；
3. 未超出 token 额度。

本次请求就用这把 Key 的 provider 与模型；Key 没有指定模型时，用平台为该 provider 配置的默认模型。你指定的模型原样
发出，不会被替换。请求过程中不会换 Key 或换模型重试；没有任何 Key 满足条件时，请求回落到平台额度。

想优先用一个模型、另一个作后备，可以把同一把 Key 录入两次、各配一个模型并排好顺序：前一条被跳过时用后一条——前一条已过期，
或前一条超额而后一条的 token 额度更高或未设额度（两条都与下文同一个月度合计比较）。列表中的箭头只在同一 provider 内调整顺序；跨 provider 的先后还取决于各 Key 的添加时间。

如果 provider 拒绝你指定的模型，请求以 `provider_rejected_model` 失败。Aster 不会悄悄改用默认模型或其他 Key 重试，
所以记录下来的调用绝不会声称用了它实际没用的模型。修正该 Key 的模型，或清空以使用默认即可。

## 编辑、额度与记录

每把 Key 都可以行内编辑——模型、token 额度、失效日期——无需重新输入 Key；改模型时与保存时一样向 provider 校验。
**重置额度**会把本月已用 token 计数清零，超额的 Key 重新可用；用量记录本身保留。

token 额度比较的是你本月所有自带 Key 的**合计**用量，而不是每把 Key 各自的用量。

每次 AI 请求都按实际运行的模型记录用量。变更会写入审计日志：对单把 Key，记录其 provider 与后四位
（设置或修改模型时另记模型）——从不记录 Key 本身；调整顺序记录新的 Key id 顺序，重置额度记录重置时间。

设置页通过 `GET /api/user/ai-keys`（需登录会话）读取你的 Key：

## Key 如何受保护

- Key 在数据库中用 PostgreSQL `pgcrypto` 加密，密钥为服务端机密。只有后四位以明文保存，用于展示。
- 只有 Aster Cloud 服务端会解密 Key，且只解密当前请求选中的那一把。它被放进发给策略 API 的签名请求，从不写入日志；
  浏览器发来的任何 Key 信息一律丢弃。
- 解密失败时请求直接失败，而不是悄悄改用平台凭证。
- 自托管 Aster Cloud 必须在 Worker 上设置 `AI_KEY_ENCRYPTION_SECRET`（至少 16 个字符），否则保存 Key 会失败。
