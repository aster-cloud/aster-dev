# Lexicons

A **lexicon** is a language pack — the keyword set, punctuation and canonicalization
rules for one human language. Aster's core grammar is language-agnostic; a lexicon
maps it onto English, 中文, Deutsch, हिन्दी, etc. All lexicons share the same
**Lexicon SPI** contract, so a policy in any language compiles to the identical core.

## How it works

The same rule, two lexicons, one compiled result:

```aster
Module Pricing.

Rule discountedPrice given amount as Int, produce Int:
  If amount greater than 100
    Return amount times 90 divided by 100.
  Return amount.
```

```aster
模块 定价。

规则 折扣价格 给定 金额 作为 整数，产出 整数：
  如果 金额 大于 100
    返回 金额 乘以 90 除以 100。
  返回 金额。
```

The compiler is told which lexicon to use via a `locale` / `lexicon` parameter. It
canonicalizes the localized keywords back to the core grammar before lowering to the
intermediate representation — which is why a Chinese policy and its English
translation produce byte-identical decisions.

## Authoring a lexicon

A lexicon is pure data plus an SPI registration — no compiler changes. You provide:

- the keyword translations (one per `SemanticTokenKind`, key set must match the
  `en-US` backbone),
- punctuation (statement terminator, e.g. `.` or Devanagari danda `।`),
- whitespace mode (e.g. `ENGLISH` vs `CHINESE` word-segmentation).

The core handles canonicalization and lowering. See the
[Reference](/docs/reference#multi-language) for the grammar contract, and try a
non-English source in the [Playground](/playground).

## Keyword aliases

A lexicon can accept **more than one spelling for the same keyword**. Aliases live
on the *recognition* side only: the canonicalizer rewrites them to the canonical
spelling before anything downstream sees them, so an aliased source and a canonical
source lower to the same Core IR and evaluate identically.

Aliases are opt-in. The bundled `en-US` / `zh-CN` / `de-DE` / `hi-IN` lexicons ship
with **none** — you add them when a team prefers different wording:

```ts
import { EN_US } from '@aster-cloud/aster-lang-ts/lexicons/en-US';

// Let this team write `Yield` wherever `Return` is expected.
const teamLexicon = { ...EN_US, aliases: { RETURN: ['Yield'] } };

compile(source, { lexicon: teamLexicon });
```

Three properties worth knowing, all of them load-bearing:

- **The canonical spelling keeps working.** Registering `Yield` does not retire
  `Return`; both compile.
- **The IR is unchanged.** Only source positions differ (an alias of a different
  length shifts columns) — the semantic tree and the evaluation result are identical.
- **Without registration the alias is just an unknown word**, and compilation fails.
  Aliases never leak between lexicons.

Because aliases collapse before lowering, they cost nothing at runtime and cannot
change a decision — which is what makes them safe to hand to non-engineers.

## Domain vocabulary

A lexicon translates *keywords*. A **domain vocabulary** translates *identifiers* —
your struct names, field names, functions and enum values — so a rule can be written
in the words a business actually uses.

Each term pairs a stable `canonical` name with a `localized` spelling:

```ts
import { vocabularyRegistry } from '@aster-cloud/aster-lang-ts/lexicons/identifiers/registry';
import { IdentifierKind } from '@aster-cloud/aster-lang-ts/lexicons/identifiers/types';

vocabularyRegistry.registerCustom('acme-tenant', {
  id: 'lending', name: 'lending', locale: 'en-US', version: '1',
  structs: [{ canonical: 'Applicant', localized: 'Borrower', kind: IdentifierKind.STRUCT }],
  fields: [{ canonical: 'score', localized: 'creditScore',
             kind: IdentifierKind.FIELD, parent: 'Applicant' }],
  functions: [], enumValues: [],
});

compile(source, { lexicon: EN_US, domain: 'lending', tenantId: 'acme-tenant' });
```

The rule is then written in the domain's words:

```aster
Module lend.

Define Borrower has
  creditScore as Int.

Rule decide given who as Borrower, produce Text:
  If who.creditScore at least 680:
    Return "APPROVED".
  Return "REFER".
```

### Evaluation inputs use canonical names

This is the one thing that catches everyone. The **source** is written in localized
words, but `evaluate` receives and returns **canonical** ones — because that is what
the compiled IR contains:

```ts
evaluate(core, 'decide', { who: { score: 700 } });      // ✅ canonical
evaluate(core, 'decide', { who: { creditScore: 700 } }); // ❌ field not found
```

Terms may also carry `aliases` (extra spellings for the same identifier) and a
`description`; both are optional, and identifier aliases work the same
recognition-only way keyword aliases do.

### Literal macros: expanding a term into fixed text

A fifth collection, `literals`, is different from the other four. Instead of
renaming an identifier it expands a term into a **fixed string** — useful when a
regulated wording has to appear verbatim and must not be retyped by hand.

Note the inversion: for `IdentifierKind.LITERAL`, `canonical` is **not** an
identifier, it is the string content that gets substituted (without quotes).

```ts
vocabularyRegistry.registerCustom('acme-tenant', {
  id: 'poem', name: 'poem', locale: 'en-US', version: '1',
  structs: [], fields: [], functions: [], enumValues: [],
  literals: [{ canonical: 'Quiet Night Thoughts', localized: 'homesick',
               kind: IdentifierKind.LITERAL }],
});
```

The trigger word then stands in for the text:

```aster
Module poem_demo.

Rule title produce Text:
  Return homesick.
```

Evaluating `title` returns `"Quiet Night Thoughts"`.

**Expression position only.** A literal macro expands to a *string*, so using its
trigger word where a name is expected — a rule name, a field, a struct — is a
compile error. `Rule homesick produce Int:` does not compile.

**The content is strictly validated** to keep an untrusted tenant from injecting
source code at compile time. Rejected: empty content, control characters or
newlines, and any quote delimiter or backslash — `"`, `\`, `「」`, `『』`, `«»`, and
the curly quotes `“ ” ‘ ’`. Ordinary visible text, including CJK characters and
punctuation, is fine (`静夜思——李白` validates).

**Trigger words must be globally unique.** A literal macro's `localized` spelling
(and its aliases) may not collide with *any* other mapping, including plain
identifiers. Because substitution is context-free, a colliding word would be
ambiguous — expanding to a string in one place and an identifier in another.

### Why it is a separate mechanism

Keyword aliases and domain vocabulary look similar but are deliberately separate:
keywords are part of the *language* and come from a trusted lexicon, while
identifiers belong to a *tenant* and are registered per tenant at runtime. Keeping
them apart is what lets an untrusted tenant supply vocabulary without being able to
redefine the grammar.

The `/demos` pages are working examples — the cat-mood demo compiles and runs a rule
written entirely in cat-care terminology, on the same engine as the credit demo.
