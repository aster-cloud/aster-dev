# Action Guard

A `Verdict` rule (see [Policies as governance](/docs/governance)) says whether an
action may happen. **Action Guard** (ADR 0040) makes that answer binding at run
time: before an AI agent does something with side effects — deletes a customer
record, moves money, sends an email — it submits the *proposed action* to Aster,
the tenant's deployed policy decides, and the agent acts only on `ALLOW`.

```text
agent proposes action ──► POST /api/v1/guard/decisions ──► deployed Verdict rule
                                                              │
        ALLOW ──► receipt on the hash chain + signed execution receipt ──► agent verifies, consumes, then acts
        DENY  ──► receipt on the hash chain ──► agent does not act
        REQUIRE_APPROVAL / ESCALATE ──► receipt + pending approval ──► a person approves, rejects, or it expires
```

Every decision — including every refusal — leaves a receipt in the tenant's
tamper-evident audit chain. An `ALLOW` additionally carries a signed, single-use
**execution receipt**: the guard is an enforcement point, not advice. The agent acts
only after it has verified that receipt and the server has accepted its one-time
*consume* (see [Execution receipts](#execution-receipts)).

## The guard request

The agent addresses a deployed policy directly by module and function, and
describes the action as *who* (principal) does *what* (action) to *which thing*
(resource), with free-form business context and the agent's declared identity:

```json
{
  "policyModule": "guard.customer",
  "policyFunction": "decide",
  "action": {
    "principal": { "id": "agent-42", "type": "agent", "roles": ["ops-bot"] },
    "action": { "name": "delete_customer_record" },
    "resource": { "type": "customer", "id": "C-1001" },
    "context": { "reason": "GDPR erasure request", "ticket": "SUP-8812" },
    "agent": { "provider": "acme-ai", "model": "acme-agent-2", "session": "s-9f3a" }
  },
  "waitSeconds": 0
}
```

Before evaluation the guard flattens the action into **one record** with fixed
keys and passes it to the rule as its only argument:

| Key | Source | Default |
| --- | --- | --- |
| `principal_id` | `principal.id` (required) | — |
| `principal_type` | `principal.type` | `"agent"` |
| `principal_roles` | `principal.roles` (at most 16) | empty list |
| `action` | `action.name` (required) | — |
| `resource_type`, `resource_id` | `resource.type`, `resource.id` | `""` |
| `context` | `context` (depth ≤ 8, ≤ 64 KB, no `null` values) | empty map |
| `agent_model` | `agent.model` | `""` |

Text fields are limited to 255 characters without control characters; a request
that breaks a limit is rejected with `400 invalid_action` before anything is
evaluated. The structured `agent` identity (`provider` and `model` required,
`version` and `session` optional) is recorded on the receipt as *declared* by the
caller; only `agent_model` reaches the rule.

The rule that reads this record:

```aster
Module guard.customer.

Define GuardRequest has principal_id, principal_type, principal_roles, action, resource_type, resource_id, context, agent_model.

@id("CUST-DEL-001")
@control("GDPR:ART17")
Rule decide given req as GuardRequest, produce Verdict:
  If req.action equals to "delete_customer_record":
    Return Verdict.require_approval("Data Protection Officer", "customer record deletion").
  Otherwise:
    Return Verdict.allow().
```

Deleting a customer record needs a Data Protection Officer; everything else is
allowed. The guard requires a `Verdict`: a rule that returns a `Bool`, a record
or text is treated as `DENY` with `reasonCode: "not_a_verdict"`.

## The decision API

`POST /api/v1/guard/decisions` takes the request above.

- **Authentication** — an API key: `Authorization: Bearer ak_…`. The key fixes the
  tenant, metering and quota; guard calls count against the same quota and
  per-key rate limit as `/evaluate`.
- **Idempotency** — send an `Idempotency-Key` header, unique per action attempt
  and reused only for network retries of that attempt. A repeat with the same key
  returns the same decision (same `decisionId` and receipt) with the *current*
  approval status, without evaluating again. Reusing a key for a different action
  returns `422 idempotency_mismatch`.
- **`waitSeconds`** — 0 to 30 (default 0). If the result is pending, the server
  re-checks every 500 ms until it is decided or the time is up.

The response is always `200` once a decision exists; keys are alphabetical and
empty values are omitted:

```json
{
  "approval": {
    "expiresAt": "2026-10-17T05:12:00Z",
    "id": "a91b0c6e-3f2d-4c55-9a51-0e7d2b8c4f10",
    "requiredRole": "Data Protection Officer",
    "status": "PENDING"
  },
  "controls": ["GDPR:ART17"],
  "decisionId": "7c1e2a90-5b4f-4d0e-8f3a-6a2d9e1b7c55",
  "effectiveOutcome": "PENDING",
  "outcome": "REQUIRE_APPROVAL",
  "policyVersion": { "id": 1730890123456, "sourceHash": "9f2c…", "version": 3 },
  "reason": "customer record deletion",
  "receipt": { "auditId": 88213, "hash": "4be1…", "prevHash": "a07d…" },
  "role": "Data Protection Officer",
  "ruleId": "CUST-DEL-001"
}
```

`outcome` is what the rule said. `effectiveOutcome` — `ALLOW`, `DENY` or
`PENDING` — is the only field an agent should act on: on `ALLOW` verify and consume
the execution receipt, then act; stop on `DENY`; on `PENDING` poll
`GET /api/v1/guard/decisions/{decisionId}` until it changes. A pending approval
expires after 24 hours by default, and an expired approval reads as `DENY`.

### No receipt, no action

The guard fails closed. The decision receipt is appended to the audit chain
*before* the decision is stored; if that write fails, the answer is `DENY` with
`reasonCode: "receipt_unavailable"` and no approval is opened. An evaluation
error or a timeout (10 seconds) is `DENY` with `reasonCode: "evaluation_failed"`.
A transient `DENY` is stored under its idempotency key, so retry with a new key.
An unknown policy or a policy without an active version is `404 policy_not_found`.

## Execution receipts

An `ALLOW` decision — issued directly, or when an approver approves — includes an
`executionReceipt`. `ALLOW` means *may be consumed once*, not *may be executed at
will*:

```json
{
  "executionReceipt": {
    "kid": "2026-11a",
    "payload": {
      "actionHash": "…64 hex…", "decisionId": "7c1e2a90-…", "expiresAt": "2026-11-16T01:05:00Z",
      "issuedAt": "2026-11-16T01:00:00Z", "kid": "2026-11a", "outcome": "ALLOW",
      "policyFunction": "decide", "policyModule": "guard.customer",
      "policyVersionId": 1730890123456, "tenantId": "team-1", "v": 1
    },
    "revision": 3,
    "signature": "<base64url, 64 bytes>"
  }
}
```

- **Signature** — Ed25519 over the `payload` canonicalised with RFC 8785 (JCS). The
  public keys are a JWKS at `GET /api/v1/guard/keys` (`kty: OKP`, `crv: Ed25519`;
  API key required, `Cache-Control: max-age=300`). `revision` is outside the
  signature and only tells executors to refresh the key set.
- **`actionHash`** — SHA-256 of the JCS-canonical request `action` object
  (`jcs-sha256/v1`). The executor computes it itself from the action it is about to
  perform.
- **Policy binding** — `policyModule` and `policyFunction` are inside the signature,
  so a receipt from a different, more permissive policy in the same tenant cannot be
  passed off as one from the policy the executor asked. `policyVersionId` is
  omitted when the decision has no stored policy version.
- **Lifetime** — 5 minutes by default (`expiresAt` is exclusive). After an approval
  the window starts at the approval time. An expired receipt cannot be renewed:
  request a new decision with a new `Idempotency-Key`.

The executor then follows one fixed order and stops at the first failure:

1. **Verify** offline: `kid` is in the JWKS (refresh once on a miss); the signature
   is valid; `tenantId`, `decisionId` and `outcome: "ALLOW"` match;
   `issuedAt − 60 s ≤ now < expiresAt`; `actionHash` equals its own hash; and
   `policyModule` / `policyFunction` are present and equal to the policy it asked.
2. **Consume**: `POST /api/v1/guard/receipts/{decisionId}/consume` with
   `{ "actionHash", "attemptId", "executorId" }`. Exactly one consume per decision
   ever succeeds (`200`).
3. **Act**, and only then.
4. **Report**: `POST /api/v1/guard/receipts/{decisionId}/result` with
   `{ "attemptId", "executorId", "status": "executed" | "failed" | "aborted" }`
   and optionally `finishedAt`, `resultHash` and `errorCode`.

| Consume response | Meaning |
| --- | --- |
| `200` | consumed: `{ consumedAt, decisionId, executionReceipt }` |
| `409 not_allowed` | no receipt — the decision is not (or not yet) `ALLOW` |
| `409 kid_revoked` | the signing key was revoked |
| `409 receipt_consumed` | already consumed (the body names the original consumer) |
| `409 receipt_expired` | `now ≥ expiresAt` |
| `409 action_mismatch` | the action changed after the decision |
| `400 invalid_consume` | malformed `actionHash`, `attemptId` or `executorId` |
| `503 receipt_unavailable` | the consume could not be recorded on the audit chain |

Anything other than `200` — including a lost response — means *do not act*. To retry
an action, request a new decision. An `ALLOW` you read anywhere else (an idempotent
replay, `GET /decisions/{id}`, a copied receipt) is not an authorisation; only your
own successful consume is.

## Reconciliation

Receipts close the front door; reconciliation looks for actions that went round it.
Every 5 minutes the policy API compares the receipt ledger with side effects that
your systems report, and records **orphans**.

Systems where effects land (tool services, business systems) report them in batches
of 1–500 with `POST /api/v1/guard/side-effects`:

```json
{ "effects": [ { "effectId": "refund-5531", "source": "billing", "occurredAt": "2026-11-16T01:02:03Z",
                 "action": { "name": "refund" }, "resource": { "type": "order", "id": "O-17" },
                 "decisionId": "7c1e2a90-…", "attemptId": "…", "actionHash": "…" } ] }
```

`effectId` is the reporter's own record key and must stay the same across network
retries of the same report (repeats are counted as `duplicates`). Report each guarded
action once per `source`.

| Orphan `kind` | Severity |
| --- | --- |
| `side_effect_without_decision` — a reported effect names no decision of this tenant | critical |
| `side_effect_unconsumed` — the decision exists but was never validly consumed | critical |
| `side_effect_mismatch` — `attemptId` / `actionHash` differ, or the decision was already matched | critical |
| `consume_on_non_allow`, `result_without_consume` — ledger states that should be impossible | critical |
| `consumed_without_result` — consumed, no result after 15 minutes | warning |
| `allow_unconsumed`, `orphan_receipt` — never consumed / chain-only noise | info |

Read the state with `GET /api/v1/guard/reconciliation` and
`GET /api/v1/guard/reconciliation/orphans?status=OPEN&kind=…`; an admin closes a
reviewed orphan with `POST /api/v1/guard/reconciliation/orphans/{id}/ack` and a
`comment`, which is recorded on the audit chain. Critical orphans also raise the
`AsterGuardBypassSuspected` alert.

## Four-eyes approval

`REQUIRE_APPROVAL` and `ESCALATE` open a pending approval. Approvers act on it
with:

```text
GET  /api/v1/guard/approvals?status=PENDING&page=0&size=20
POST /api/v1/guard/approvals/{approvalId}/approve   body: {"comment": "…"}   (comment optional)
POST /api/v1/guard/approvals/{approvalId}/reject    body: {"comment": "…"}   (comment required)
```

Send a JSON body (at least `{}`) with `Content-Type: application/json`. A
successful call returns the decision with its new `effectiveOutcome` — `ALLOW`
after approval, `DENY` after rejection — and appends an approval event to the
audit chain that points back to the decision receipt's hash.

Separation of duties is enforced on resolved identities. The approver must not be
the principal that proposed the action, nor the user who submitted the decision
request, and must not use the same API key; any match is
`403 segregation_of_duties`. For `REQUIRE_APPROVAL` the approver must also hold
the required role, otherwise `403 role_mismatch`. `ESCALATE` carries no role, so
any other member may resolve it.

### Reviewing the decision input

Approvers see what the rule decided on through a masked view:
`GET /api/v1/guard/approvals/{approvalId}/input`. Fields the policy declares `@pii`
appear as `{ "$pii": { "level": "L2", "category": "email" } }`; a value whose shape
does not match the declaration appears as `{ "$pii": { "level": "unknown" } }`; and
keys the policy does not declare are not shown at all — all undeclared keys of an
object collapse into one `"$undeclared"` entry, because a key name can itself be
personal data. Other declared text is passed through the same pattern redactor as
the logs (e-mail, phone, card numbers and so on).

A holder of the required role may reveal the declared `@pii` values of a `PENDING`
approval with `POST /api/v1/guard/approvals/{approvalId}/input/reveal` (body `{}`);
each first reveal per person is recorded on the audit chain. Undeclared content can
never be revealed, and `ESCALATE` items cannot be revealed. When approving or
rejecting, send the `inputSnapshotHash` of the view you looked at; if the view has
changed since, the answer is `409 input_snapshot_mismatch` — refresh and review
again.

### Business roles (ADR 0042)

Roles are not taken from the caller's word. In Aster Cloud, a team owner or admin
grants **business roles** — free text such as `Data Protection Officer`, at most
16 per member — to team members (personal workspaces set them on the user). They
travel with the member's API key and the internal signed channel, and the guard
matches the required role exactly, case-sensitively, against that verified set.

Approvers do not need to call the API by hand: the **Approvals** inbox in the Aster
Cloud dashboard lists pending approvals across every workspace you belong to. You
can act on an item when you hold its required role (or it is an escalation);
members without the role — owners and admins included — see the item read-only. When a dashboard or API
execution in Cloud returns `REQUIRE_APPROVAL` or `ESCALATE`, Cloud opens the guard
decision from the execution's evidence, links it to the execution record, and
notifies the role holders in the app.

## Guarding an agent: `aster-guard`

[`@aster-cloud/aster-guard`](https://www.npmjs.com/package/@aster-cloud/aster-guard)
(0.3.0; Node ≥ 24, ESM only; source on
[GitHub](https://github.com/aster-cloud/aster-guard)) is the reference executor.
It provides:

- **`GuardClient`** — a TypeScript SDK. Its `run` method performs the whole
  sequence — hash the action → decide (waiting while `PENDING`) → verify the
  execution receipt → consume → call your function → report the result — in that
  fixed order. There is no option to skip verification or consume. The lower-level
  methods (`check`, `get`, `waitFor`, `listApprovals`, `getApprovalInput`,
  `revealApprovalInput`, `approve`, `reject`, `keys`, `verifyReceipt`, `consume`,
  `reportResult`, `hashAction`, `reportSideEffects`) stay public.
- **`aster-guard-mcp`** — an MCP proxy. It wraps an upstream MCP server, exposes its
  tools under the same names, and runs every `tools/call` through the same sequence
  before forwarding it.
- **`@aster-cloud/aster-guard/tool`** — the tool-side check for `--isolation auth`
  (below).

```bash
npm install @aster-cloud/aster-guard
```

```ts
import { GuardClient } from '@aster-cloud/aster-guard';

const guard = new GuardClient({
  baseUrl: 'https://policy.aster-lang.dev',
  apiKey: process.env.ASTER_API_KEY!, // ak_…
  policyModule: 'guard.customer',
  policyFunction: 'decide',
  principal: { id: 'agent-42', type: 'agent' },
  tenantId: 'team-1', // the API key's tenant; checked against the receipt
});

const outcome = await guard.run(
  { action: { name: 'delete_customer_record' }, resource: { type: 'customer', id: 'C-1001' } },
  async () => deleteCustomerRecord('C-1001'), // called only after consume returned 200
  { executorId: 'billing-worker@pod-3', approvalTimeoutMs: 300_000 },
);
// outcome.kind: 'executed' | 'blocked' | 'pending' | 'failed'
```

A receipt whose `policyModule` / `policyFunction` is missing or differs from the
client's configured policy is rejected as `blocked` with `receipt_invalid`
(`detail: policy_mismatch`); nothing is consumed or executed.

### The MCP proxy

An MCP host launches the proxy instead of the upstream server. In Claude Desktop's
`claude_desktop_config.json` (Cursor's `mcp.json` uses the same `mcpServers` shape):

```json
{
  "mcpServers": {
    "guarded-filesystem": {
      "command": "npx",
      "args": [
        "-y", "-p", "@aster-cloud/aster-guard", "aster-guard-mcp",
        "--upstream", "npx -y @modelcontextprotocol/server-filesystem /tmp",
        "--base-url", "https://policy.aster-lang.dev",
        "--policy", "guard.customer/decide",
        "--principal-id", "agent-claude",
        "--tenant-id", "team-1",
        "--isolation", "network",
        "--tools", "write_file,move_file",
        "--resource-from", "path",
        "--approval-timeout", "300"
      ],
      "env": { "ASTER_GUARD_API_KEY": "ak_xxxxxxxx" }
    }
  }
}
```

The API key is read only from the environment variable (`--api-key-env` changes its
name) and is not passed on to the upstream process. When wrapping an upstream,
`--tenant-id` and `--isolation` are required, and `--tools` lists the tools that may
be exposed (without it every tool is exposed and the proxy warns at start-up).

For each tool call the proxy uses the tool name as `action.name` and the normalised
tool arguments (keys sorted, `null` kept) as both `context` and the arguments it
forwards — one object, so what was decided is what runs. The exception is a per-tool
`digestArgs` mapping in `--config`: those keys reach the policy as
`{ "$sha256": … }` digests, while the upstream still receives the original values. `--resource-from <argName>`
takes that top-level argument as the resource id (a value over 255 characters or
with control characters becomes `sha256:<hex>`). Only a consumed `ALLOW` is
forwarded. `DENY`, a `PENDING` that outlasts `--approval-timeout`, and any failed
verification or consume return a tool error (`Blocked by Aster Guard: …`) with a
structured `asterGuard` payload whose `status` is `denied`, `pending` or `blocked`.
Calling the tool again is a new decision.

Without an upstream the proxy instead exposes five governance tools: `guard_check`,
`guard_status`, `guard_list_approvals`, `guard_approve`, `guard_reject`.

#### HTTP upstreams and listen mode

- `--upstream-url <url>` connects to an upstream over Streamable HTTP instead of
  starting a child process (`--upstream-auth-env <name>` sends that variable as a
  bearer token to the upstream).
- `--listen <host>:<port>` serves the proxy itself over stateless Streamable HTTP
  (`POST /mcp`, request body ≤ 1 MiB). Agents are registered in `--agents-file`
  (only the SHA-256 of each agent's token is stored), and each agent is decided as
  its own principal. `GET /healthz` is liveness; `GET /readyz` is `200` only after
  a successful upstream `tools/list` in the last 30 seconds.
- In listen mode an unreachable or dropped HTTP upstream does not stop the process:
  the proxy reconnects in the background with capped exponential backoff (from
  about 0.5 s up to 30 s, with jitter). Until it is ready, `/readyz` is `503` and a
  `tools/call` is refused **before** any decision with
  `{ "asterGuard": { "status": "blocked", "reasonCode": "upstream_unavailable" } }`.

#### Isolation: the agent must not reach the raw tool

A proxy only helps if the model cannot call the tool directly. `--isolation` states
how that is guaranteed, and the bypass test suite proves it:

- `network` — the upstream accepts connections only from the proxy. A stdio child
  process satisfies this by construction; for an HTTP upstream it is your network
  policy (for example `aster-agents → aster-guard → aster-tools` namespaces in
  Kubernetes).
- `auth` — the proxy attaches the consume ticket to the forwarded call
  (`params._meta["io.aster/guard-consume"]`), and the tool verifies it with
  `@aster-cloud/aster-guard/tool` before doing anything.
- `network,auth` — both, so either still holds if the other fails.

#### Server version

0.3.0 requires a policy API that signs the policy address into receipts (live on
`policy.aster-lang.dev`). Against an older or rolled-back self-hosted API, every
action is refused with `policy_mismatch` (fail-closed) — pin
`@aster-cloud/aster-guard@0.2.0` there. When upgrading a self-hosted deployment,
deploy the API first, wait at least one receipt lifetime (5 minutes), then upgrade
the executors.

### Known limit: host timeouts

MCP hosts commonly time a request out after **60 seconds** (the MCP TypeScript
SDK's default), while a human approval can take minutes or hours (ADR 0040 §10).
Set the host's request or tool-call timeout to at least `--approval-timeout`, or
lower `--approval-timeout` to fit the host. Otherwise the host cancels the call
first, and an approval that arrives later is not forwarded. For long approvals,
prefer an agent that uses `GuardClient` and polls the decision on its own
schedule.
